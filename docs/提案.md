# 判断层（Judgment Layer）· 立项书 v0.1

> 一句话：现有记忆系统存**事实**，这个项目存**判断**——而且判断可以被后来的证据推翻，全程留痕。

---

## 一、为什么这不是又一个记忆轮子

mem0、letta、zep 这类项目解决的是「存什么、怎么检索、怎么不忘」。单位是 **fact**。

fact 的宿命是被引用。「用户喜欢蓝色」存下来，只能被读出来贴到上下文里。

我要的是另一层单位：**判断**。判断不描述世界，判断改下一步怎么做。

| | 记忆库 | 判断层 |
|---|---|---|
| 单位 | 事实 | 判断 |
| 入库 | 能记的都记 | 写不成动作的不许进 |
| 冲突 | 无版本，两条矛盾一起躺着 | 加强 / 限定 / 推翻，旧条降级挂靠 |
| 生效 | 检索出来当参考 | 直接改指令，不照做要理由 |
| 失效 | 靠人工删 | 命中次数决定，用不用说了算 |

## 二、一条判断必须带四样

缺一样就不准入库。缺反例的那种，长三个月必然变成教条。

![判断的解剖](img/02-judgment-anatomy.png)

硬规矩：**写得成一个具体动作，才算判断**。写不成动作的，只准进知识层备份，不准进判断层生效。

---

## 三、书怎么长成判断

这条链是本项目最核心的自证：原料不是凭空来的，是从 16 本书里一步步压出来的。

![书到判断](img/02b-book-to-judgment.png)

链条上每一环都有文件：书库笔记、知识条目、指令、日志。谁想核，从头核到尾。

## 四、能核实的账

不给 PPT，给数据。本机长期日志，全部真实，可复现（条数持续增长，见 docs/measurements/）。

![命中分布](img/03-hits-distribution.png)

关键在一个反直觉的结论：**遗忘由「用不用」决定，不由「感觉重要」决定。**

那条记账让 `journal search` 每次命中 +1，淘汰时先走没被回头找过的。目前 143 条（60%）一次都没被找过——它们不重要吗？不知道，但它们没被用过。

这一点现有记忆项目几乎都不做。它们默认记忆是对的、都该留着。

## 五、一条真实的推翻链

讲机制不如给案例。token 消耗那件事，我从 11-05 说错到 11-06 改口，全程有文件。

![版本链](img/04-version-chain.png)

要注意这不是推翻，是**限定**——把适用范围收窄，不是把话收回。

三种改法要分清：
- **加强**：新证据支持旧判断，置信度上调
- **限定**：旧判断只在条件下成立，收窄适用范围
- **推翻**：旧判断错了，降级但不删，留痕说明为什么变

存事实的系统处理不了这三种，因为它没有「我昨天说错了」这个概念。

## 六、仓库里放什么

**最初计划的目录**（保留原文，作为「想法 → 实际」的对照）：

```
judgment-layer/
├── CONCEPT.md            五层模型 + 判断的解剖（图 1、2）
├── JUDGMENT_SCHEMA.md    判断的数据结构：命题/条件/反例/出处/置信/版本
├── REVISION.md           加强·限定·推翻 的判定规则与留痕格式
├── ADMISSION.md          准入标准：写不成动作的不许进
├── FORGETTING.md         命中计数 → 淘汰算法（附本机真实数据）
├── VERIFY.md             极差检验：同一问题，加判断前后答得一样吗
├── DISTILL.md            书 → 知识 → 判断的提炼流程
├── CASE-token.md         完整的推翻链案例（图 4）
├── measurements/
│   ├── hits-distribution.json      真实分布
│   └── reproduce.py                一条命令重算
└── templates/
    ├── journal-lite/      精简版分级日志（无插件依赖）
    └── owner-profile.md   画像模板（已脱敏）
```

**实际落成的结构**（写代码时发现：八份说明文档不如一份协议 + 能跑的校验器）：

```
judgment-layer/
├── PROTOCOL.md            协议正文（原来那八份合并成这一份）
├── README.md              外面看的那一层
├── data/judgments.jsonl   真实的判断记录
├── src/judgment_layer/    校验器 + CLI（六个子命令）
├── tests/                 规则测试 + 编码坑回归
├── tools/                 自检、出图、实验脚本
├── docs/                   提案、实测、攻防、自查、状态
└── examples/              从书到判断的完整示例
```

差别最大的一处：原计划是「写八份文档讲清楚」，实际是「写一份协议 + 写一个能跑的实现」。

理由很实在——**规章制度写八份没人读，能跑的实现会立刻暴露哪些条款是空的。**

`templates/` 那一层没做，因为「把别人的记忆搬过来」这件事还没验证过价值，先不占位。

## 七、诚实的风险

**一、样本只有一个。** 240 条数据是我和一个人三个月处出来的，没有第二个人验证过。别人照搬，长出来的可能完全不是这回事。这是最大的漏洞，必须在 README 里明写。

**二、第四层最难落地。** 「改指令而不是塞参考」依赖宿主支持——得有办法把判断写进系统提示或预设里。换个 agent 框架，这层可能得重做。

**三、容易被当成哲学。** 讲判断、讲推翻、讲留痕，写得不好就是空谈。所以这个仓库必须以数据打头，概念放后面。

**四、我可能高估了它的独特性。** 有人在做 belief revision 那一套学术方向。真去查了再说，不装。
