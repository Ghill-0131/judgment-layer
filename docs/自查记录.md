## 已确认能绕过 V11 的路径

V11 是刚补的规则，最年轻，也最容易被绕过。实测五条：

### 1. scope 尾随空格 —— 最严重的绕过

```
A: scope = ["重要表达"]
B: scope = ["重要表达 "]    ← 多了个空格
```

V11 报 **0 条**。两条动作相反的判断并存，协议放行。

**原因**：`by_scope` 用原始字符串做 key，`"重要表达"` 和 `"重要表达 "` 是两个不同的 key。

**危害**：这条绕过不需要任何恶意，写的人手滑加个空格就中了。而且它不报错，静默失效——最难查的那种。

**修法**：scope 入 key 前先 `strip()`，并拒绝首尾带空格的 scope（V3 加一条）。

### 2. related_to 只写 id 不写 relation

```json
{"related_to": [{"id": "j-b"}]}
```

没有 `relation` 字段，V11 也放行（报 0 条）。

**危害**：协议第四节要求「判定三者中哪一个，必须写下来」，但代码只检查 id 是否存在，不检查关系声明是否合法。

**修法**：`related_to` 每项必须有 `relation`，且值必须在 `加强/并立/限定` 里，否则报 V11。

### 3. relation 随便填也放行

```json
{"related_to": [{"id": "j-b", "relation": "随便写写"}]}
```

报 0 条。`加强/并立/限定` 这个枚举在 V9 里查了 `relation`，但没查 `related_to[].relation`。

**修法**：同上，枚举校验。

### 4. related_to 塞不存在的 id

```
A: related_to = [{"id": "j-NOT-EXIST"}]
```

这个**没绕过**——A 会被报，因为 j-NOT-EXIST 不在场景内。设计正确。

### 5. related_to 塞非字符串元素

```json
{"related_to": [12345]}
```

不崩溃，会报出来（因为 12345 不在场景 id 集合里）。行为可接受，但类型该拦。

## 我自己没想清楚的

**hits 的语义漏洞**（协议第 6 节）

「命中」定义为「被检索且真正影响了一次行为」。

但：一条判断被用了、结果错了，算不算 hit？

- 算 → 错误判断越用越稳固，越难被淘汰
- 不算 → 谁判定「这次用对了」？

现在协议回避了这个问题，只说「真正影响」。这是回避不是解决。

**candidate 30 天自动归档**

如果这 30 天那个用户压根没用这个系统（比如出差、放假），好东西会被清掉。

**修法候选**：改成「30 天内系统被使用过、但这条没被裁决」才归档。但这需要记录「系统最近被用了吗」，协议里没有这个字段。

**archived 永不删除**

十年后是什么样？协议说每年人工扫一次。但人工扫几千条是不现实的。

**修法候选**：archived 满 N 年且零命中的，降级成纯文本快照（不进检索、不占主库），而不是留在库里。
